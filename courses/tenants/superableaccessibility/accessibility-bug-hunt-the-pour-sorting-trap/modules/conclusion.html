Debrief: What Just Happened

Everything on the previous page was intentional. Here's what was actually going on, and which WCAG principle each failure maps to.

The on-screen instructions promised Space to lift, arrow keys to move, Space again to drop, and Escape to cancel. Only the Space-to-lift toggle was actually wired up in the JavaScript — arrow key movement and Escape were never implemented. This is an extremely common real-world pattern: a custom drag-and-drop widget built for mouse users, with keyboard support bolted on just far enough to look present in a code review, but not far enough to actually complete the task.

The fix: implement full keyboard equivalents for every mouse interaction the widget supports, and test the interaction to completion with a keyboard before shipping — not just "does something happen when I press a key."

The drop zones sat inside a container with a fixed pixel width and overflow: hidden. At normal zoom there was room to spare, so nothing looked wrong. At 200% zoom the visual viewport shrank below that fixed width, and because the container hid overflow instead of allowing scroll, the "Understandable" and "Robust" columns were pushed out of view with no way to reach them.

The fix: use relative/fluid widths (or CSS Grid/Flexbox that's allowed to wrap) instead of fixed pixel widths for layout containers, satisfying WCAG 1.4.10 Reflow.

That bright, button-styled "Click here for a keyboard alternative" box was a plain <div> — no <button>, no tabindex, no keyboard event handling. A mouse user sees an obvious call-to-action. A keyboard-only user's focus indicator skips right past it, and there's no way to even discover it's there.

The fix: use real interactive elements (<button>, <a href>) for anything clickable, never a styled <div> with a click handler.

Submitting the activity graded each zone by swapping in a green or red border/background — no icon, no text label, nothing but color to distinguish "correct" from "incorrect." On top of that, the feedback panel appeared without ever moving keyboard focus into it, so a screen reader user would get no indication anything had happened at all after clicking Submit.

The fix: pair color with a text label or icon (WCAG 1.4.1), and move focus into any dialog that appears, announcing it and returning focus to the trigger on close.

The takeaway

None of these four bugs would show up in a quick visual scan, and all four are things real teams ship regularly. The good news: each one is testable in under a minute with nothing but a keyboard and your browser's built-in zoom — no assistive tech or specialized skills required. That's the habit worth building.
