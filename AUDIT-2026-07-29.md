## 2. Critical findings — security

These are the ones I would fix before anything else. Several are chainable into a full platform compromise.

**Status update (2026-07-31): C-1 through C-7 verified fixed in code** — session/tenant binding (`bind_session_to_tenant`, `enforce_tenant_session_binding`, `is_platform_admin`), the seeded `password123` admin removed, `isTrustedXapiLaunch()` replacing the query-param bypass, login/register throttling, api.php CSRF via `check_csrf_token()`, and error.log relocated outside the web root. Each fix is documented inline at its original location. Findings below are left as originally written for reference; only the A-series (accessibility) and F-series (functional bugs) remain unverified.

### C-1. Any tenant admin is a platform super-admin — ✅ Fixed

`platform_admin.php:17`
```php
$pdo = get_db_connection('local-dev');   // connects to platform DB
if (!isset($_SESSION['user_id']) || !$_SESSION['is_admin']) { ... }
```

The connection is forced to the platform database, but the authorization check reads `$_SESSION['is_admin']` — a flag set by `login.php:33` when logging into **any** tenant. An admin of the smallest client tenant can open `platform_admin.php` and provision tenants, change any tenant's plan, suspend accounts, and rewrite `custom_domains.json`.

There is no check that the session user is an admin *in the platform database*.

### C-2. `?tenant=` grants cross-tenant access, carrying your privileges with you — ✅ Fixed

`config.php:117-123` — `resolveTenantKey()` accepts `?tenant=<anything>` with no authorization check and pins it into the session. Session identity (`user_id`, `is_admin`) is never scoped to a tenant. Consequences:

- `admin.php?tenant=victim` — `admin.php:22` only checks `is_admin`, then every operation uses `resolveTenantKey()`. A tenant A admin fully administers tenant B: uploads courses, rewrites branding, reads the user list, mints invitation keys.
- `index.php?tenant=victim` — `index.php:510` uses `$is_admin` to bypass the `hidden` course filter, exposing another tenant's private catalogue.
- `api.php?tenant=victim` — see C-3.

### C-3. `api.php` writes your user ID into any tenant's database — ✅ Fixed

`api.php:21-81`. The tenant key comes straight from the request. If the session user doesn't exist in that tenant's DB, lines 57-81 **create** them — copying the row from `local-dev` including `is_admin` and the password hash, or inserting a stub. After that:

- `get_progress_logs` (line 232-245) re-reads `is_admin` from the *victim* tenant DB and, if true, honours an arbitrary `target_user_id` — reading any learner's completion and telemetry history.
- `mark_complete` and `log_interaction` write into the victim tenant.

Additionally, **no endpoint in `api.php` calls `verify_csrf_token()`**, and `config.php:41` sets `session.cookie_samesite = 'None'` over HTTPS, so these POSTs are cross-site forgeable.

### C-4. Every auto-created tenant database ships a known admin credential — ✅ Fixed

`config.php:890-894`, inside `ensure_tables_exist()`:
```php
$stmt = $pdo->query("SELECT COUNT(*) FROM users");
if ($stmt->fetchColumn() == 0) {
    // INSERT ... VALUES (1, 'jacob@jacobwood.me', <hash of 'password123'>, 'Jacob Wood', 1)
}
```

`get_db_connection()` creates the directory and schema on demand, and `resolveTenantKey()` accepts any tenant key from the URL. So `GET /index.php?tenant=anything-at-all` provisions a fresh SQLite database seeded with an **administrator account whose password is `password123`**. Chained with C-1, an anonymous visitor can create a tenant, log into it as admin, and reach the platform admin panel.

`setup_tenant.php:20` and `platform_admin.php:36` also default `$adminPassword` to `'password123'`.

### C-5. Course access control is bypassed by two query parameters — ✅ Fixed

`player.php:97-100`
```php
$is_xapi_launch = (isset($_GET['endpoint']) && isset($_GET['auth']))
    || (isset($_GET['xAPILaunchService']) && isset($_GET['xAPILaunchKey']));

if (!$has_permission && $access['type'] !== 'public' && !$is_xapi_launch) { /* deny */ }
```

The values are never validated — only their presence is checked. `player.php?course_id=paid-course&endpoint=x&auth=y` opens any restricted course to anyone.

### C-6. No brute-force or rate limiting anywhere — ✅ Fixed

`login.php` has no attempt counter, lockout, or delay. `register.php` has no CSRF token and no rate limit. `api.php`'s `log_interaction` accepts unauthenticated guest writes with no cap — an unbounded disk-fill vector against `interaction_telemetry`.

### C-7. `error.log` is served from the web root — ✅ Fixed

`config.php:14` writes to `__DIR__ . '/error.log'`. `.htaccess` contains no `deny` rule and no `Options -Indexes`. In production the file is fetchable at `https://superablelearning.com/error.log`. The current copy contains absolute filesystem paths, stack traces, and the developer's local directory layout. It is correctly gitignored — the problem is only that it lives inside the document root.

`.htaccess` also sets no security headers at all: no CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, or HSTS.

### C-8. XSS surfaces from course-package data

Course manifests and module HTML are attacker-influenced (any tenant admin can upload a ZIP), and several paths inject them without escaping:

| Location | Issue |
| :--- | :--- |
| `index.php:664` | `<a href="<?= $course_url ?>">` — `$course_url` comes from `manifest.properties.url`, echoed with no escaping. A `"` breaks out of the attribute. |
| `player.php:322` | `manifest: <?= json_encode($manifest) ?>` inside `<script>` — `json_encode` without `JSON_HEX_TAG` does not escape `<`, so a `</script>` inside any manifest string closes the block. |
| `player.php:601, 894, 961` | `btn.innerHTML = \`${btn.textContent.trim()} <span...>\`` — module titles (harvested from course `<h1>` tags by `pre_process_manifest_modules`) re-injected as HTML. |
| `player.php:694, 720, 1030, 1032` | Module titles interpolated into `aria-label="..."` and into innerHTML templates without escaping. |
| `sl-components.js:66-84` | Accordion `${title}` and `<h${level}>` interpolated from author-supplied attributes. |

`player.php:736-741` deliberately re-executes `<script>` elements found in fetched module HTML. That is by design for course interactivity, but it means **any course author has script execution on the LMS origin with the learner's session cookie**. Worth an explicit architectural decision (sandboxed iframe with a postMessage bridge is the usual answer).

### C-9. CSS injection through tenant metadata

`config.php:600-627` writes tenant branding values into a `<style>` block using `htmlspecialchars()`. That prevents an HTML breakout but does nothing against CSS injection — a value like `red; } .skip-link { display:none } .x{` is passed through intact, defeating the very accessibility guards `validateCustomCss()` exists to enforce. Branding values are never validated as hex colors.

Related: `config.php:687` builds `href="<?= $supportHref ?>"` from `support_contact` metadata; a `javascript:` value survives `htmlspecialchars()`.

## 3. Severe findings — accessibility (WCAG 2.2 AA)

### A-1. Duplicate IDs in the accordion break `aria-controls` on every page that uses more than one

`sl-components.js:56-57`
```js
const headerId = `jw-accordion-header-${index}`;
const panelId  = `jw-accordion-panel-${index}`;
```

`index` restarts at 0 for **each `<sl-accordion>` instance**. The player's sidebar (`player.php:374-386`) creates one accordion per module group, each holding a single item at index 0 — so every group's trigger emits `id="jw-accordion-header-0"` and `aria-controls="jw-accordion-panel-0"`. All triggers point at the first group's panel, and `aria-labelledby` on every region resolves to the wrong heading.

Fails **4.1.1 Parsing / 4.1.2 Name, Role, Value**. Affects the sidebar of every grouped course and the `components-course` demo pages.

### A-2. Double screen-reader announcements on every toggle component

`.gemini/rules/accessibility_and_lms_standards.md` lines 29-31 say plainly: do not fire live-region alerts on `aria-expanded` toggles, because screen readers already announce state changes.

The shipped library does exactly that:
- `sl-components.js:97-98` — accordion announces `"{title} expanded"` on top of native `aria-expanded`.
- `sl-components.js:215-216` — tabs announce `"{label} tab selected"` on top of native `aria-selected`.
- `sl-components.js:482-483` — click-reveal.
- `sl-components.js:1421, 1435` — modal announces `"Modal dialog opened"` on top of the native `<dialog>` announcement.

Same pattern in the app: `index.php:702/720` and `player.php:872-885` put content into a `role="status"` / `aria-live` container **and** move focus into it — announced twice.

### A-3. The live-region utility is unreliable

`sl-components.js:11-28`. Two problems:

1. The region is created and populated in the same interaction, 100 ms apart. Live regions must exist in the DOM before the mutation for reliable announcement; 100 ms after `appendChild` is a race.
2. `aria-live` is mutated on an existing element to switch polite/assertive. NVDA and JAWS do not reliably honour a changed `aria-live` value on a live node. The standard fix is two permanent regions (one polite, one assertive) rendered in the page shell.

`player.php:717` has the same shape — `<div id="completion-container" aria-live="polite">` is created *as part of* the content injection, so its first update is likely silent.

### A-4. Focus is lost during async saves

`player.php:828-830`
```js
btn.textContent = "Saving...";
btn.disabled = true;
btn.focus();          // no-op — a disabled button cannot receive focus
```

Focus falls back to `<body>`. On success, focus is moved to the completion heading (line 885); on error, to the alert (line 909). Between those, keyboard and screen-reader users are stranded at the top of the document with no status announcement. Same pattern at `player.php:934-938`.

Also on the failure path in `markCurrentComplete`, `btn` is never restored — it stays disabled reading "Saving..." permanently.

### A-5. `.btn` has no visual styling, and one instance is invisible — ✅ Fixed (2026-07-31)

Fixed: `.btn` (`style.css:1055`) now has a default `background-color`/`color` so any bare `.btn` renders visibly instead of inheriting `a { color: var(--color-primary) }`. Modifier classes (`.btn-primary`, `.btn-outline-light`, etc.) already set their own background/color and override this cleanly. Added the missing `.btn-full` class (`width: 100%`), used by `login.php:120` and `register.php:164`. `.btn-danger` and `.btn-outline` (no `-light` suffix) turned out to be self-contained in `packager.php`'s own inline `<style>` block — not actually broken, despite appearing unstyled from a `style.css`-only search.

Original finding, for reference:

`style.css:1055-1071` defines `.btn` with layout, radius, and `border: 2px solid transparent` — but **no `background-color` and no `color`**. The colour comes from modifier classes (`.btn-primary`, `.btn-teal`, `.btn-accent`, `.btn-outline-light`). Several key controls use `.btn` with no modifier, and `.btn-full` / `.btn-danger` / `.btn-outline` are referenced but **do not exist in `style.css`**:

| Location | Markup | Rendered result |
| :--- | :--- | :--- |
| `index.php:595` | `<a class="btn btn-sm">Log In</a>` inside `.site-header` | Inherits `a { color: var(--color-primary) }` = **#3B7A57 text on the #3B7A57 header — 1:1 contrast, invisible.** |
| `index.php:664` | `<a class="btn btn-sm">Start Course</a>` | Transparent; primary CTA of the dashboard renders as plain text |
| `index.php:713, 735` | `<button class="btn">` | Browser-default grey |
| `login.php:99` | `<button class="btn btn-full">Login</button>` | Browser-default grey |
| `register.php:138, 159` | `.btn btn-full`, `.btn` | Browser-default grey |

The header "Log In" case is a hard **1.4.3 Contrast (Minimum)** failure on a guest-facing control.

### A-6. Unlabelled `<select>` elements that navigate on change

`index.php:227` and `login.php:122`
```html
<select class="form-control" onchange="if(this.value) window.location.href=...">
```

Two failures:
- No `<label>`, no `aria-label`, no `id`. The accessible name is empty — **4.1.2 / 3.3.2**.
- Selecting an option triggers a page navigation with no explicit activation — **3.2.2 On Input**.

### A-7. `aria-label` on non-interactive elements is ignored

`index.php:630` — `<div class="badge" aria-label="Course Completed">`. A plain `<div>` with no role has no accessible-name calculation; the label is dropped by most screen readers. The visible text happens to convey the same thing, so nothing is lost in practice, but the intent doesn't land.

`index.php:666-671` — the `<a>` carries `aria-label="Start course: X (opens in a new tab)"` **and** a `<span class="sr-only">(opens in a new tab)</span>`. The `aria-label` overrides all content, so the `sr-only` span is dead code.

### A-8. Unwrapped emoji, contradicting the project's own rule

The blueprint (section 4) requires all decorative emoji to carry `aria-hidden="true"`. Missed at:
- `index.php:643` — `<span class="badge badge-secondary">🔒 Locked</span>` announces "locked padlock Locked".
- `index.php:255, 267, 274, 279, 285` — six `.feature-icon-box` divs on the platform homepage carry bare emoji with no `aria-hidden`, while the sibling at line 261 has it. Inconsistent.

### A-9. No `prefers-reduced-motion` support in the platform stylesheet

`style.css:97` sets `scroll-behavior: smooth` globally, plus `transition` on ~20 selectors and `transform: translateY()` hover lifts on `.card`, `.tenant-chip`, and `.pricing-card`. There is **no `@media (prefers-reduced-motion: reduce)` block anywhere in `style.css`**.

Notably, `admin.php:399-401` *injects* a reduced-motion safety block into compiled tenant CSS, and `packager.php:352` includes one for generated courses — so the platform enforces on others what it doesn't do itself.

### A-10. Sticky header with no scroll offset

`style.css:906-914` — `.site-header { position: sticky; top: 0; z-index: 100 }`, roughly 76 px tall. There is no `scroll-padding-top` on `html` and no `scroll-margin-top` on focusable elements.

- The homepage's in-page nav (`#about`, `#why-superable`, `#features`, `#architecture`) lands its targets underneath the header.
- Tabbing to a control just below the fold can leave it obscured — **2.4.11 Focus Not Obscured (Minimum)**, new in WCAG 2.2 AA.

### A-11. Dark mode is roughly 10% implemented

`style.css:627-652` defines dark tokens for `body`, `.card`, `.form-control`, `table`, `table th`, and `.text-neutral-mid`. Everything else keeps a hardcoded light surface:

| Selector | Hardcoded |
| :--- | :--- |
| `style.css:736` `.tenant-chip` | `background-color: #FFFFFF` with `color: var(--color-primary)` — in dark mode the branding engine *lightens* `--color-primary`, putting a light colour on white |
| `style.css:758` `.workspace-finder-card` | `background: white` |
| `style.css:783` `.pricing-card` | `background: white` |
| `style.css:306` `.dropdown-menu` | `background-color: white` |
| `style.css:200` `.cta-button-light` | `background-color: white` |
| `player.php:176` `.sidebar-nav` | `background: white` |
| `player.php:262` `.content-area` | `background: white` with `color: var(--color-text-dark)` |
| `player.php:1028` resume card | `background-color: #f8fafc` |
| `sl-components.js:2112-2116` | Quiz cards: inline `background: #ffffff`, `color: #1e293b` |

The player — where learners spend all their time — has no working dark mode at all. The toggle button only exists on the tenant dashboard (`index.php:586`); it's absent from the platform homepage, login, register, help, pricing, and the player, and there is no `@media (prefers-color-scheme: dark)` fallback. Theme is applied in `DOMContentLoaded` (`index.php:747`), so dark-mode users get a white flash on every navigation.

### A-12. Hover-only dropdown menu

`style.css:330-332` — `.nav-item-dropdown:hover .dropdown-menu { display: block }`. No `:focus-within`, no keyboard path, no dismiss mechanism. Fails **2.1.1 Keyboard** and **1.4.13 Content on Hover or Focus** wherever it's used.

### A-13. Heading structure in the player

`player.php` has **no `<h1>` anywhere in the shell**. The course title at line 333 is a `<div class="text-xl font-bold">`, the sidebar opens at `<h2>` (line 344), and `<main>` opens at `<h2>Loading Course...</h2>` (line 352). Module HTML supplies an `<h1>` only after JS loads. The blueprint's own standard (accessibility rules, section "Strict Sequential Heading Hierarchy") says the active panel's primary title should be `<h1>`.

Focus management on module change is otherwise done correctly (`player.php:798-806`).

### A-14. Root font size pinned

`style.css:98` — `html { font-size: 16px }`, with all heading sizes in `px` (lines 121-126). This overrides the user's browser font-size preference. Page zoom still works, so it isn't a 1.4.4 failure, but it defeats the setting low-vision users are most likely to have configured.

## 5. Architecture & consistency observations

### The platform violates its own tenant CSS rules

`validateCustomCss()` (`config.php:446-506`) rejects tenant stylesheets that use `@import`, external `url()`, or `outline: none`. The platform's own `style.css` does all three:

- Line 8: `@import url('https://fonts.googleapis.com/...')` — also the worst-performing way to load a font (serial, render-blocking).
- Line 76: `button:focus { outline: none; }`
- Line 290: `.form-group input:focus { outline: none; }`

(The `:focus-visible` `!important` guards at lines 70-82 and 660-668 do restore the keyboard indicator, so this is not a live failure on modern browsers — but the double standard is worth resolving, and those two guard blocks are exact duplicates of each other.)

### "Zero-dependency" is not accurate at runtime

`player.php` loads from three third-party origins with no SRI hashes and no fallback:
- `cdnjs.cloudflare.com` — Font Awesome 6.5.2 (line 134)
- `cdn.jsdelivr.net` — Mux Player (line 151)
- `fonts.googleapis.com` — Atkinson Hyperlegible (line 141, plus again via `renderTenantBrandingCss`, plus again via `style.css:8` — **the font is requested three times**)

Beyond performance, Google Fonts calls from a platform marketing FERPA/HIPAA compliance are a GDPR exposure worth a deliberate decision. Self-hosting Atkinson Hyperlegible would remove two of the three.

### Session model doesn't match the multi-tenant model

The blueprint's central claim is strict per-tenant isolation. The session carries `user_id`, `full_name`, `is_admin` with **no tenant binding**, while `resolveTenantKey()` is free to change tenants mid-session from a query parameter. This single mismatch is the root cause of C-1, C-2, and C-3. Adding `$_SESSION['tenant_key']` at login and asserting it equals `resolveTenantKey()` on every authenticated request would close all three.

### PostgreSQL migration blockers

The roadmap targets Postgres. Current blockers:
- `module_progress.user_id` and `user_permissions.user_id` are `INTEGER` but receive `'guest_' . session_id()` strings (`index.php:16`, `player.php:15`, `api.php:54`). SQLite's dynamic typing tolerates this; Postgres will reject it outright.
- `interaction_telemetry.user_id` is `TEXT` with no foreign key, inconsistent with every other table.
- `datetime('now')` (`config.php:1128, 1157`) is SQLite-specific.
- `INSERT OR IGNORE` / `INSERT OR REPLACE` (`api.php:69`, `setup_tenant.php:50`) are SQLite-specific.

## 6. What's genuinely good

Worth recording so it doesn't get refactored away:

- **Focus management on module navigation** (`player.php:798-806`) is correct — it finds the new heading, makes it programmatically focusable, and moves focus there.
- **The modal uses native `<dialog>` + `showModal()`** (`sl-components.js:1419`), which gets focus trapping, Escape handling, and inert background for free. This is the right call.
- **The branding contrast engine** (`config.php:588-618`) progressively darkens/lightens tenant colours until they pass 4.5:1 in both themes. That's genuinely thoughtful and rare.
- **`course_importer.php`** has a real extension whitelist, a path-traversal guard, and quota enforcement before extraction.
- **`.gemini/rules/accessibility_and_lms_standards.md`** is a high-quality standards document. Most of the A-series findings above are places where the code drifted from rules that are already written down correctly.
- **The `sl-` / `jw-` dual registration** via empty subclassing (`sl-components.js:1867-1871`) is the correct way to alias custom elements without constructor reuse exceptions.
- **CSRF is properly implemented** in `config.php` and correctly applied in `admin.php`, `platform_admin.php`, and `index.php` — the gap is that `api.php`, `login.php`, and `register.php` never call it.
